D.5.2 结论与承载机制

16 条候选 → 0 条 syncTriggers 联动 / 16 条否决（v1.1：20 条候选 → 0 联动 / 20 否决；v1.2：24 条候选 → 0 联动 / 24 否决）。承载机制 v1.0 六类 → v1.1 七类 → v1.2 仍是这七类、一类未增：规则承载的显式写入（6 + C-19 = 7，+ C-23 = 8）+ 一个动作写多个归属对象（6 + C-17 = 7，+ C-21 = 8）+ 同对象推进（1 + C-18 = 2，+ C-24 = 3）+ 事件通告（2）+ 明确不写（1 + C-22 = 2）+ （v1.1 新增第七类）以对端为准的对账（C-20 = 1）—— 合计 24，逐条可归、无遗漏无重复。

v1.1 判据补记：C-20 是本项目第一次出现「执行事实的对账写入」候选 —— 之所以仍判为否决，判据是写入方向：联动（syncTriggers）的定义是「本域某对象的变更驱动另一个对象的写入」，而回执对账是外部事实驱动本对象的结论字段，属 B-AUTO（自动行为）范畴。「以对端为准」不构成联动的先例已在 O-IGN D.5.3 立过（O-CLC 是其镜像侧）。 [已确认]

v1.2 判据补记（本批最重要的一条方法论）：C-21「模板实例化」是全项目形态上最像 syncTriggers 联动的一条 —— 它是"一个编目对象的变更驱动一批业务对象生成"，正是元文件里 syncTriggers 的教科书场景。判为否决的理由不是"它特殊"，而是判据本身：① 触发源是人工提交（FUNC-01 事务内），不是"A 已变更后自动写 B"；② 写入方向单向（模板 → 只被读、不写模板；R-20 把"不回写、不跟随"钉成规则，等于主动放弃了这条联动）；③ 被写的三处（集群 / 节点 / 参数）同属一个聚合。结论可以推广：只要一个动作是"人工一次提交、事务内写齐一个聚合"，无论它读几个来源对象，都不是联动；联动只在"无人为介入的自动跨聚合写"里存在。这条判据在 v1.0（C-01 三连写）与 v1.1（C-17 步骤连锁）各用过一次，本批第三次使用 —— 同一判据三次给出同一答案，是它可信的证据，不是它失效的证据**。 [已确认]

D.5.3 本域特有结论

本域的健康字段是全项目唯一「多源汇聚写入点」 —— 五类上游事件（执行机、交付域、仓库、资产、证书）与探活结论都写同一个 health 字段，靠双源写入口径表（谁在什么条件下能写什么值、谁能清除谁不能）维持一致（R-08）。其他域的写入是「每个动作写自己的对象」，本域是汇聚点 —— 这正是「降级不自动恢复」必须成为铁纪律的结构性原因：多源写入若无写权限表，字段会被最后一个写入者覆盖。十方对照：结论同、成因各不同。 [已确认]
